# 包管理

## 包管理认识

### 什么是包管理？

包管理是自动化处理第三方代码（包）的下载、安装、升级、删除以及依赖关系解析的过程。它解决了手动引入库时“下载源码、复制文件、手动加载顺序”的原始低效问题。

### 包管理工具

#### npm

默认的包管理工具，随同Node.js 一起安装。 拥有广泛的支持和活跃的社区，可轻松找到并安装大多数前端依赖项。但因为它使用的是**单一的全局依赖树**，在处理依赖冲突时可能会出现问题。此外，cnpm是npm国内镜像，能在国内网络环境加速下载速度，但它不是独立的包管理工具，可能与某些依赖不兼容。

#### yarn

由 Facebook 开发的包管理工具，旨在解决 NPM 的一些问题。能够**并行下载和缓存包，引入锁定文件**，可确保团队成员在使用相同的包版本上保持一致。（同npm一样，其操作是找到压缩包->解压->拷贝到项目的node_modules.由于每个项目都会缓存，这会造成硬盘空间的浪费。）

#### pnpm

通过将依赖项链接到一个**共享的存储库**来减少重复的下载。允许在不同的项目之间**共享相同的依赖项**。（全局仓库只存一份文件，项目里创建的只是硬链接）

#### 三者的区别

· NPM：Node.js 官方内置，无需额外安装。采用扁平化依赖树结构，早期版本安装速度较慢。通过 package-lock.json 锁定版本。
· Yarn：由 Facebook 推出，采用并行安装机制，安装速度优于早期 NPM。使用 yarn.lock 锁定版本，并引入离线缓存功能。
· PNPM：通过全局存储 + 文件链接的方式管理依赖，不同项目复用同一份包文件，节省磁盘空间。使用 pnpm-lock.yaml 锁定版本，且依赖结构更严格，不会出现未声明即可用的情况。

> 早期npm和yarm采用分层并行模式，其解析逻辑为先构建依赖树，再逐层扫描；安装方式为先下载顶层依赖，完成后再下载下一层。其痛点在于，若某一层级的一个包由于网络卡住，后续所有依赖都会原地待命。
>
> pnpm采用流式流水线机制，只要解析出一个包的地址，就立刻开启下载和解压进程，无需等待同层级的其他包。解析、获取、链接三阶段在不同包间异步交错进行。

### 工程结构

文件结构：根目录包含 package.json（入口）、锁文件（Lockfile）、node_modules（依赖实体）、src（源码）等。
· package.json：项目配置清单。
· node_modules/：存放所有安装的第三方依赖包。
· 锁文件（如 package-lock.json / yarn.lock / pnpm-lock.yaml）：记录精确版本号，保证团队环境一致。
· src/：项目源代码目录。
· public/ 或 dist/：存放静态资源或构建后的输出文件。
· 配置文件（如 .gitignore、vite.config.js、tsconfig.json 等）：各类工具的环境配置。

### 配置规范

#### package.json 配置

- name：项目/模块名称。(必备属性)

  包名会成为模块`url`、命令行中的一个参数或者一个文件夹名称，任何非`url`安全的字符在包名中都不能使用，可使用 `validate-npm-package-name` 包来检测包名是否合法。

  - `description`用于添加模块的的描述信息，方便别人了解该模块。

    `keywords`用于给模块添加关键字。写好 `description` 和 `keywords` 有利于模块获得更多更精准的曝光。

  -  `author` 描述包的主要作者，`contributors` 描述贡献者信息

  - `homepage` 用于指定该模块的主页。

    `repository` 用于指定模块的代码仓库。

    `bugs` 指定一个地址或者一个邮箱，对你的模块存在疑问的人可以到这里提出问题。

- version：项目版本号。(必备属性)

  `VERSION`是一个遵循`SemVer`规范的版本号配置，`npm install` 时将到npm服务器下载符合指定版本范围的包

- scripts：定义可执行的命令行脚本（如 "start": "node index.js"）。

- dependencies：生产环境依赖，项目运行时需要（npm install --save）。 - -
- devDependencies：开发环境依赖，仅构建/测试时需要（npm install --save-dev）。
- main：模块入口文件路径（通常为 index.js）。
- engines：指定项目所需的 Node.js 版本（可选）。

### 环境优化

#### 阿⾥ npm 镜像

阿里云提供了国内镜像服务（淘宝镜像），配置后可将包下载源指向国内服务器，提升安装速度。

```bash
npm config set registry https://registry.npmmirror.com
```

配置后，NPM、Yarn、PNPM 均会使用该镜像源。不可直接使用 cnpm 命令，因为它可能不生成锁文件，导致版本管理不规范。



#### 包管理工具最核心解决的问题

减少版本冲突问题，实现文件的自动下载和安装。同时能检测漏洞及版本更新（不发生版本冲突/重复下载的问题）。

- “不⽤包管理能不能做项⽬”？

  可以做简单的小项目，但现代工程化的项目不可。没有包管理将无法处理传递依赖（A 依赖 B，根本不知道还要去下载 B）。同时版本升级变得困难，需要手动覆盖文件。

#### 依赖版本冲突一般是怎么产生的？

项目依赖树中两个或多个不同的顶层/传递依赖对同一个包要求了不兼容的版本，就产生了冲突。

暂未遇到此种情况，但在网上找到了相关例子。

升级框架版本时，项目原本使用 Vue 2.x，后来引入一个 UI 组件库，该库的 peerDependencies（对等依赖）指定必须 Vue@3.x，而项目仍是 Vue@2.x，此时安装就会触发冲突警告或错误。

解决方法是使用 npm overrides 或 yarn resolutions 强制覆盖传递依赖版本，或者逐步升级主框架版本。

#### pnpm 和 npm 的 node_modules 结构差异，为什么会影响安装速度与磁盘占用？

npm是扁平化结构，所有依赖都放在node_modules目录下，每个项目都有一个依赖副本，安装时每个项目都会出现缓存，导致硬盘空间浪费。

pnpm所有版本都存放在全局store中，node_modules只留硬链接，指向全局store中的真实文件。
